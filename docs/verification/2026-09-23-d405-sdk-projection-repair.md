# D405 RGB-D 投影问题：旧 SDK 缺陷已修复上线，残余分割问题单独保留

本次响应操作员“反复标定仍有 RGB-D 问题”的反馈。保留机械臂现场，不触发抓取或发布失能命令。以下同帧相机证据与手眼跨姿态验证分开记录。

## 已确认的底层问题

同一 D405，序列号 `260522277974`，固件 `5.17.0.10`，彩色 `BGR8 640×480 30 FPS`：

| 查询来源 | fx | fy | cx | cy |
| --- | ---: | ---: | ---: | ---: |
| 现有 pyrealsense2 2.55.1.6486 | 438.600403 | 438.416962 | 317.779266 | 245.357147 |
| 隔离官方 librealsense 2.56.5 | 395.768280 | 395.602753 | 317.996124 | 244.833984 |

两次查询没有打开相机流或写入设备。新版原生深度内参仍为 fx=fy=389.453400，改变的是 D405 VGA 彩色投影计算，不是深度单位或物理板尺寸。

官方修复 [Fix D405 VGA resolution intrinsics calculation](https://github.com/realsenseai/librealsense/commit/68a6fe3e54229a995ce07bb75206cd45ff757d29) 修正了 640×480 路径的 ISP 缩放及裁剪内参；[v2.56.3 发布记录](https://github.com/realsenseai/librealsense/releases/tag/v2.56.3) 列出 D405 UV 和内参错位修复。新 SDK 直接查询结果与该公式预测一致，并接近先前九姿态数据支持的约 398 焦距。不能把此问题归因于用户没有正确摆板。

旧 SDK 错误会同时影响其深度到彩色对齐和下游反投影。只改 YAML 的 fx/fy 而仍按旧 SDK 对齐，会让 RGB、深度像素及 K 继续不一致。原设备标定、深度比例及手眼文件均不应据此任意修改。

## 为什么之前没有消除

1. 先前 RGB 投影修正仅完成离线验证，生产相机未启用，本次仍使用旧 SDK 与旧投影。
2. Python 3.8 的 PyPI 预编译包最高停在 2.55.1；普通 pip 升级不足以取得修复。新版 Python 接口需隔离编译，不能仅把“pip 最新兼容版本”视为最新 SDK。
3. 相机节点之前只从设备更新 depth_scale，K 仍来自 YAML，且缺少运行 SDK/设备/profile 来源记录。升级 SDK 后如果继续使用旧 YAML K，还会造成新的不一致。
4. 分割程序将 3×3 侵蚀后的整个深度候选设为强前景，桌垫进入种子后难以再由 RGB 纠正。它放大了底层错位，但不是改小掩膜即可解决的唯一问题。
5. 手眼标定影响跨姿态的基座位置一致性，不能修复同帧 RGB 与 depth 的轮廓。之前新手眼的第九独立姿态仍未通过，未部署，不能称为“新标定已经修好又失效”。

## 已完成的源码修复与离线证据

`RealSenseManager` 从实际活动流读取内参、畸变、设备/固件/SDK、原生 depth→color 外参、对齐、实际滤波及投影修正状态。`camera_node` 在第一帧前一次更新 `/camera` 的 K、depth_scale 和 runtime_profile；断线重连也刷新。模拟数据明确使用配置来源。原图像话题、frame_id、分辨率、帧率、滤波及控制逻辑不变。38 项相机相关测试通过。

用先前九组、27 个已保存标定源帧，不重新拟合 SDK 内参，比较每姿态首/中/末三帧的中位指标：旧 SDK 的深度 Z 偏差绝对值约 22.4–27.5 mm，官方新公式约 1.39–2.56 mm；重投影 RMS 约 0.45–0.63 px 降至 0.10–0.16 px。该处是光轴 Z 差，不应与历史文档约 20–23 mm 的板面法向距离混为同一指标。新版实际查询 K 的复验另存 JSON。

旧 bag 只含已经对齐/滤波的深度，因此离线最近邻映射无法恢复原生像素覆盖、遮挡及滤波前数据。当前物体的桌垫点 (380,265) 在离线重映射中从高出桌面 8.42 mm 变为 -1.01 mm并退出候选，另一个点仍有 5.33 mm 残余；不能把 SDK 修复描述为已经解决全部掩膜误差。新的前景内核实验遗漏深色侧面且仅保留 65.12% 深度种子，未通过原 85% 要求，没有部署或放宽条件。

在确认任务 IDLE/active=false 后，只关闭 `/supervisor_camera`。同一现场分别使用旧 SDK、新 SDK 各取三组 RGB、native depth、aligned-unfiltered 和 aligned-filtered；约 9.4 秒后启动 `alicia-camera-sdk-20260923.service`。相机服务的 PartOf 绑定当前 ROS 主服务，未来完整启动通过 sensors.launch 的相机专用 wrapper 使用同一隔离 SDK。

实际新相机已发布 640×480、原话题、camera_link 图像。`/camera/runtime_profile/sdk_version=2.56.5`，fx=395.768280、fy=395.602753，depth_scale不变。ROS 主服务、只读监督、归档队列全都保持 active。任务仍 IDLE，joint_direct_mode仍false，正向使能请求状态保持 PENDING；未发送失能或运动命令。

刷新同一 unknown/direct 模式的观测代次，清除旧投影下的感知与规划缓存，没有启动规划/抓取或改变控制归属。代次3后观测到跟踪失锁；一次15秒的代次4追踪先记录几次 `initial_instance_rgb_instance_reaches_search_boundary`，随后取得 acquired/tracked。不能据此声称已长期稳定。

必须保留反例：新SDK三帧阴影误入分别0、410、45像素，第二帧仍吞入整个阴影窗。相对第一帧，其未滤波高度变化的深度分量约+3.669 mm，平面重拟合分量约−0.141 mm。说明残余主要已存在于对齐后但未空间滤波的局部深度中，被4mm前景阈值和硬前景锁定放大；尚不能唯一归因原生传感器或对齐像素处理。没有放宽85%一致性门槛、接入未经验证的掩膜裁剪或启用旧RGB投影补偿。

真实数据、12种滤波/SDK重放结果及边界图位于本机会话 `sdk_native_comparison_analysis/`。旧SDK内参错误已在生产相机纠正；残余深度/分割和手眼跨姿态问题没有冒充修复通过。


## 残余硬前景信任问题的有界实验

在真实新版三帧上，另以5×5局部实测平面、≤0.5mm拟合残差、≤8mm局部深度跨度建立侧面法向种子，阈值预固定30/45/60°；评估窗口不参与种子生成。45°候选保留深色前侧477/477/476像素，桌垫误入0/5/0、阴影0/8/1，显示侧面几何有助于纠正阴影。然而其原深度seed保留率83.02%/80.99%/81.21%，未通过现有85%约束，所以未部署。30°第二帧虽达到85.45%，仍吞入245个阴影像素，证明单纯保留率通过也不能证明轮廓正确。

后续分割修正必须重新验证“哪些深度种子可信”，并覆盖不同物体、侧面与阴影；不能为了本物体通过而降低门槛或硬编码颜色。当前生产分割与抓取条件保持，新的侧面候选仅在诊断目录中。系统性SDK投影修复已上线；完整未知物体抓取、残余轮廓稳定性以及跨姿态手眼验证尚未完成。
